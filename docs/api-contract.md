## 1. Introduction

### 1.1 Purpose

This document defines the application programming interface (API) contract for OfflineLink Zambia.

It establishes the conventions, endpoint inventory, identifier formats, timestamp standards, data exchange principles and error-handling expectations that govern communication between the frontend application and backend server.

The contract serves as a shared technical reference for frontend and backend development.

Both implementation workflows must follow the same approved contract. Neither side should independently introduce endpoint paths, payload fields, identifier formats or response structures.

### 1.2 Scope

The API supports:

- Application health monitoring.
- Agricultural record retrieval.
- Agricultural data persistence through the approved synchronization workflow.
- Full-record synchronization.
- Change-log synchronization.
- Operation processing status and receipt retrieval.
- Structured validation and error reporting.

The API is designed around an offline-first client. Field-officer record mutations must first be persisted locally and placed in the synchronization queue. Normal online connectivity must not introduce a separate direct-write path that bypasses the synchronization protocol.

### 1.3 Contract Status

The following are established API conventions:

- `/api/v1` as the canonical API prefix.
- `/api/v1/health` as the canonical versioned health endpoint.
- UUIDv4 entity identifiers generated by the client.
- UUIDv4 operation identifiers generated by the client and reused during retries.
- UTC ISO 8601 timestamps.
- Structured JSON error responses.
- Local-first field-officer mutations.
- No DELETE operation in the initial API scope.

Exact synchronization payload schemas, receipt structures and detailed error status mappings remain subject to specification and approval.

## 2. Contract Principles

All API development must follow these principles.

### 2.1 JSON Communication

The application API will use JSON request and response bodies over HTTP.

Request and response structures must be documented and validated.

### 2.2 API Versioning

The canonical application API prefix is:

`/api/v1`

New application endpoints must use this prefix unless an approved architectural decision establishes otherwise.

### 2.3 Stable Identifiers

Entity identifiers and operation identifiers must use the approved UUIDv4 format.

Identifiers must remain consistent across frontend persistence, synchronization submissions and backend processing.

### 2.4 Timestamp Standard

Timestamps must use ISO 8601 with UTC timezone information.

The expected representation is equivalent to:

`2026-11-11T08:30:00Z`

The backend and frontend must apply the same timestamp interpretation.

### 2.5 Validation

Request data must be validated before it is accepted for processing.

Invalid data must produce a documented structured error response.

### 2.6 Contract Consistency

Frontend types and backend schemas must represent the same API contract.

A change to field names, requiredness, identifier types or response meaning must be reflected in this document and the affected implementation tests.

### 2.7 Synchronization Integrity

Client-generated operation identifiers must remain stable across retries.

A successful HTTP response must not automatically be interpreted as verified synchronization completion.

### 3.1 Important Write-Path Rule

The agricultural resource POST and PATCH entries describe the resource API inventory. They must not create an alternative normal write path for field officers.

The field application must:

1. Validate the user's input.
2. Persist the record locally.
3. Create the corresponding local synchronization operation.
4. Retain that operation until it is successfully processed.

Central server mutations must follow the approved synchronization protocol.

Any administrative or research use of direct resource write interfaces must be explicitly defined and must not compromise the experimental comparison.

### 3.2 Endpoint Scope Control

The initial API must not introduce additional operations outside the approved research requirements without review.

DELETE endpoints are excluded from the initial API scope.

Pagination is deferred unless justified by actual requirements or implementation evidence.

## 4. Identifier Conventions

### 4.1 Entity Identifiers

All supported agricultural entities must use UUIDv4 identifiers generated by the client.

The initial entity identifiers are:

| Entity | Identifier |
|---|---|
| Farmer | `farmer_id` |
| Farm | `farm_id` |
| Crop | `crop_id` |
| Observation | `observation_id` |

The identifier must remain unchanged between local persistence and central synchronization.

### 4.2 Operation Identifiers

Each logical synchronization operation must receive a client-generated UUIDv4 operation identifier.

The identifier must:

- Be created once for the logical operation.
- Be stored with the local operation.
- Remain unchanged during retries.
- Be submitted to the server.
- Be used for duplicate recognition.
- Be associated with processing evidence or a receipt.

A retry must not generate a new operation identifier.

### 4.3 Identifier Scope

The exact database uniqueness constraints, operation identity scope and idempotency retention rules are defined through the synchronization protocol and database design.

## 5. Timestamp and Data Conventions

### 5.1 Timestamp Fields

The initial agricultural data dictionary includes:

- `created_at`
- `updated_at`

Additional operation and synchronization timestamps may be required by the final protocol.

All timestamp values must use UTC ISO 8601 representation.

### 5.2 Optional Fields

Optional fields must have explicitly documented nullability.

The frontend and backend must agree on whether an optional field may be omitted, supplied as null or required.

### 5.3 Relationships

The initial agricultural relationships are:

- A farm is associated with a farmer.
- A crop is associated with a farm.
- An observation is associated with a crop.

The backend must validate the relevant relationships before accepting persisted data.

### 5.4 Pagination

Pagination is not mandatory in the initial API specification.

If a justified requirement introduces pagination, a single consistent convention must be documented and used across applicable list endpoints.

## 7. Error Response Contract

### 7.1 General Principle

API errors must use a consistent JSON structure.

The initial proposed error envelope is:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "details": []
  }
}
```

### 7.2 Error Fields

| Field | Purpose |
|---|---|
| `error.code` | Machine-readable error identifier |
| `error.message` | Human-readable error description |
| `error.details` | Additional validation or processing details |

The exact structure and allowed contents of `details` must be finalized before implementation.

### 7.3 Error Handling Requirements

The API must:

- Return structured errors for invalid requests.
- Avoid exposing internal stack traces.
- Avoid exposing secrets or sensitive server configuration.
- Distinguish validation failures from retryable processing failures.
- Provide sufficient information for the client to handle rejected synchronization operations.

### 7.4 HTTP Status Mapping

The exact HTTP status-code mapping for validation errors, missing records, conflicts, duplicate operation delivery and server failures remains to be finalized.

The mapping must be documented consistently across frontend and backend implementations.

## 8. Synchronization API Contract

Synchronization endpoints provide the interface between the offline-first client and central server.

### 8.1 Full-Record Synchronization

**Endpoint:**

`POST /api/v1/sync/full-record`

Purpose:

Submit queued logical operations using the full-record synchronization representation.

The request must carry sufficient information to identify each logical operation and the complete record representation required by the approved protocol.

### 8.2 Change-Log Synchronization

**Endpoint:**

`POST /api/v1/sync/change-log`

Purpose:

Submit queued logical operations using individual change entries.

The request must carry sufficient information to identify each logical operation and represent the corresponding change according to the approved protocol.

### 8.3 Shared Operation Information

Each submitted logical operation must include the information required by the approved protocol, including:

- Stable operation ID.
- Operation type.
- Entity type.
- Entity ID.
- Operation payload or change payload, depending on the selected method.
- Client creation time or sequence metadata where required.
- Protocol or version identifier.

The exact JSON structures and field constraints are not yet frozen.

### 8.4 Processing Responses

The server response must provide sufficient evidence for the client to determine:

- Which operation IDs were received.
- Which operations were accepted and processed.
- Which operations were rejected and why.
- Whether a repeated operation was recognized.
- Whether durable processing evidence or a receipt is available.

A transport-level success response alone is not sufficient to mark a logical operation as verified complete.

### 8.5 Operation Status Retrieval

**Endpoint:**

`GET /api/v1/sync/operations/{operation_id}`

Purpose:

Retrieve the processing status or receipt associated with a logical operation.

The exact response fields and status lifecycle must be finalized in `sync-protocol.md`.

## 9. API and Synchronization Compatibility

The API must remain compatible with the approved synchronization protocol.

### 9.1 Shared Rules

Both synchronization endpoints must follow:

- Stable operation identity.
- Equivalent logical operation ordering.
- Duplicate-prevention requirements.
- Shared retry policy.
- Processing acknowledgement requirements.
- Final-state verification requirements.
- Comparable experimental measurement rules.

### 9.2 Method-Specific Representation

The two methods may use different payload representations.

However, they must not introduce differences in the underlying logical workload or correctness expectations.

### 9.3 Frontend and Backend Compatibility

The frontend and backend must use the same:

- Endpoint paths.
- Identifier formats.
- Field names.
- Timestamp conventions.
- Request schemas.
- Response schemas.
- Error codes and response structures.
- Synchronization operation semantics.

Any incompatible contract change must be reviewed before implementation.

## 12. Contract Change Management

Any proposed API contract change must:

1. Identify the affected endpoint, field or behavior.
2. Explain why the change is required.
3. Assess its impact on frontend/backend compatibility.
4. Assess its impact on synchronization correctness and research validity.
5. Be reviewed before implementation.
6. Update this document and affected specifications.
7. Include relevant regression and integration tests.

Material changes must be recorded in `docs/decisions/`.

The frontend and backend must not independently modify the contract.
